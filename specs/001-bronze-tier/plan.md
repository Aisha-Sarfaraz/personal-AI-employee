# Implementation Plan: Bronze Tier Foundation

**Branch**: `001-bronze-tier` | **Date**: 2026-02-17 | **Spec**: [specs/001-bronze-tier/spec.md](spec.md)
**Input**: Feature specification from `/specs/001-bronze-tier/spec.md`

## Summary

Build the Bronze Tier (Foundation Layer) of the Personal AI Employee FTE system. This establishes: Obsidian vault as memory/GUI, one working filesystem watcher (watchdog library), 5 agent skills for the reasoning pipeline (triage → handbook check → plan → execute → dashboard), file-based HITL approval workflow, DEV_MODE action executor, Python orchestrator with health monitoring, and PM2 process management. Silver/Gold tiers are structurally visible as stub files.

## Technical Context

**Language/Version**: Python 3.10+
**Primary Dependencies**: watchdog (filesystem monitoring), pyyaml (YAML frontmatter), python-dotenv (env vars)
**Storage**: Local filesystem — Obsidian-compatible Markdown vault with YAML frontmatter
**Testing**: pytest + pytest-cov
**Target Platform**: Windows 10 (dev), cross-platform compatible (POSIX signal handling with Windows fallback)
**Project Type**: Single Python project with file-based data layer
**Performance Goals**: Event-to-triage < 10 seconds, full pipeline < 60 seconds (excluding human approval wait)
**Constraints**: DEV_MODE only (no real external actions), single-threaded orchestrator, sequential FIFO processing
**Scale/Scope**: Single user, <100 vault files at a time, 1 active watcher

## Architecture Decisions

### AD-1: Vault Folder Position as State Machine

Items move between vault folders to represent state transitions. No separate database or state file needed for pipeline state. The orchestrator scans all folders on startup to resume from wherever items are.

**Rationale:** Obsidian vault IS the GUI — users see state by looking at folders. Simplest possible state management. Crash-safe: vault is on disk, always consistent.

### AD-2: Keyword-Based Triage (No LLM)

Bronze uses dictionary-based keyword scoring instead of calling an LLM for classification.

**Rationale:** Zero external dependencies, deterministic, testable, fast. Constitution S2.1 requires Bronze to work with minimal setup. LLM-based triage can be added in Silver tier.

### AD-3: step_action_ids for Idempotent Re-execution

Plan metadata stores a `step_action_ids` dict mapping step numbers to approval request UUIDs. On re-execution, the executor checks existing approval status instead of creating duplicate requests.

**Rationale:** Discovered as a critical bug in previous implementation. Without this, every re-run of the executor creates new APPROVAL_REQUIRED files, making it impossible to track which approval maps to which step.

### AD-4: Sequential FIFO Processing

Orchestrator processes one pipeline item at a time in FIFO order. No parallelism.

**Rationale:** Constitution S7.1 mandates queue-based sequential execution. Bronze tier doesn't need throughput. Eliminates race conditions and simplifies testing.

### AD-5: DEV_MODE Action Simulation

All external actions (send_email, create_invoice, etc.) are simulated in Bronze. The action executor logs what WOULD happen without actually doing it.

**Rationale:** Constitution S8.2(SEC6) requires DEV_MODE. Bronze has no MCP servers wired. Silver tier will connect real MCP servers.

## Implementation Phases

### Phase 1: Setup
- Create all directories with `__init__.py` files
- Create `requirements.txt` (watchdog, pyyaml, python-dotenv, pytest, pytest-cov)
- Create `config/settings.yaml` with all configuration
- Create vault folders with `.gitkeep`
- Create `vault/state/` for watcher persistence

### Phase 2: Core Libraries
- `src/core/vault.py` — read_file, write_file, move_file, list_folder, read_frontmatter_file, write_frontmatter_file with atomic writes (temp + os.replace)
- `src/core/frontmatter.py` — parse_frontmatter, write_frontmatter, create_standard_metadata
- `src/core/audit_logger.py` — log_action writes AUDIT_*.md to /Logs
- `src/core/approval.py` — create_approval_request (→ /Pending_Approval), check_approval_status (scans Approved/Rejected/Pending_Approval), 24h expiry

### Phase 3: Vault Knowledge Files
- `vault/Dashboard.md` — Initial template (will be auto-regenerated)
- `vault/Company_Handbook.md` — 6 sections: Communication Rules, Financial Thresholds, Approval Requirements, Behavioral Constraints, Task Processing Rules, Changelog
- `vault/Business_Goals.md` — Business objectives document

### Phase 4: Watcher Layer
- `src/watchers/base_watcher.py` — ABC with check_for_updates(), create_action_file(), dedup (processed IDs set + JSON state), configurable poll interval, error isolation per item
- `src/watchers/filesystem_watcher.py` — watchdog Observer + FileSystemEventHandler, creates FILE_{timestamp}_{name}.md in /Inbox, handles binary/empty files with type:unknown
- `src/watchers/gmail_watcher.py` — Stub: class GmailWatcher(BaseWatcher), raises NotImplementedError
- `src/watchers/whatsapp_watcher.py` — Stub: class WhatsAppWatcher(BaseWatcher), raises NotImplementedError
- `src/watchers/finance_watcher.py` — Stub: class FinanceWatcher(BaseWatcher), raises NotImplementedError

### Phase 5: Reasoning Skills
- `src/skills/triage_inbox.py` — Scan /Inbox, classify type + priority by keyword scoring, move to /Needs_Action with updated frontmatter, log via audit_logger
- `src/skills/check_handbook.py` — Read Company_Handbook.md, classify_action_risk (financial thresholds), classify_financial_risk (amount → risk tier), validate_action → ValidationResult
- `src/skills/plan_task.py` — Read task from /Needs_Action + handbook, generate PLAN_*.md in /Plans with type-specific steps, approval flags per risk level
- `src/skills/execute_plan.py` — Read plans from /Plans, execute steps sequentially, create approval requests for HIGH/CRITICAL, check approval status, persist step_action_ids, move completed plans to /Done
- `src/skills/update_dashboard.py` — Scan all vault folders, count items, check watcher health, regenerate Dashboard.md with status tables

### Phase 6: Action Layer
- `src/actions/action_executor.py` — dispatch map: action_type → handler, DEV_MODE simulation, handlers: send_email, create_invoice, post_social, update_calendar, file_operation, unknown action handling (skip + log warning)

### Phase 7: Orchestration
- `src/orchestrator.py` — Multi-watcher registry, start watchers as daemon threads, scan loop (triage → plan → execute → dashboard), signal handlers (SIGINT/SIGTERM), startup vault scan for resume
- `src/watchdog_monitor.py` — Background thread: check watcher threads alive, detect stuck plans (age > threshold), verify vault folder integrity
- `ecosystem.config.js` — PM2 config: name "fte-orchestrator", script "src/orchestrator.py", interpreter "python", auto-restart, log output to logs/

### Phase 8: Tests
- Unit tests for all core modules (vault, frontmatter, approval, audit_logger)
- Unit tests for watchers (base, filesystem)
- Unit tests for all skills (triage, handbook, plan, execute, dashboard)
- Unit tests for action executor
- E2E integration test: drop file → full pipeline → Done
